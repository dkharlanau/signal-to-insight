OpenTelemetry traces: reconstruct observed causality, not business truth

OpenTelemetry correlates timed spans through trace identity, propagated context, hierarchy and links so distributed work can be reconstructed diagnostically across service boundaries.

WHY THIS MATTERS

A trace is more than a list of logs: it carries correlation and causal structure across processes. But that structure is telemetry, not an automatic execution ledger. The distinction matters when observability data is used to debug work versus prove authorization, side effects or durable business outcomes.

KNOWLEDGE DELTA

What this source changes in the existing model.

OpenTelemetry refines the project's broad observability concept into a concrete causal telemetry model: spans share trace identity, context propagation carries correlation across boundaries, and links preserve asynchronous causality without turning telemetry into an authoritative execution ledger.

Refines

Observability

Source says: OpenTelemetry traces assemble distributed operations from spans connected by trace identity, hierarchy, propagated context and causal links.

Previously: The enterprise-agent case introduced observability only as structured telemetry around consequential execution, without a detailed distributed tracing mechanism.

Project interpretation: The source makes observability operational at the trace layer while preserving the earlier boundary that telemetry is not automatically the authoritative record of business execution.

Distributed trace

Source says: Spans sharing a trace ID and parent relationships are assembled into one distributed view of observed work across components.

Previously: The graph had a broad observability concept but no explicit end-to-end causal trace structure.

Project interpretation: A trace becomes the reusable diagnostic structure for reconstructing an observed distributed path rather than a generic collection of logs.

Trace context propagation

Source says: Trace and span identity are propagated across process/network boundaries so downstream spans can remain correlated with upstream work.

Previously: No prior graph concept modeled transport of tracing identity across distributed boundaries.

Project interpretation: Propagation is the mechanism that turns local spans into a distributed causal view instead of disconnected component telemetry.

Span link

Source says: OpenTelemetry links spans when operations are causally associated but do not fit a normal parent-child relationship, especially for asynchronous work.

Previously: The graph had no tracing-specific representation for asynchronous causal association outside a direct tree hierarchy.

Project interpretation: Links prevent asynchronous work from being forced into misleading synchronous parent-child semantics.

MENTAL MODEL

01 · Start

Root span

A request begins with a trace ID and root span describing the first observed operation.

02 · Propagate

Carry trace context

Trace/span context crosses the network boundary with the downstream request.

03 · Continue

Child span

The downstream service creates a new span in the same trace and records the parent relationship.

04 · Decouple

Async span link

Queued work that starts later can be causally associated through a link even when direct nesting is inappropriate.

Source problem

Distributed operations cross service/process boundaries, making isolated component logs insufficient for reconstructing the observed end-to-end path and causal relationships.

Source thesis

Represent operations as spans, propagate trace/span context across boundaries, assemble parent-child hierarchy under shared trace identity, and use span links for causal relationships that do not fit normal nesting.

EXAMPLES

synchronous request

A frontend calls a catalog service and then a payment service.

Does propagated trace context let the downstream spans join one hierarchy that explains where latency and failure occurred?

asynchronous work

A request enqueues a job that is processed minutes later by another consumer.

Should the later work be represented with a span link rather than pretending it has a normal synchronous parent-child lifetime?

business execution evidence

A trace shows a successful span for updating a customer record.

What separate evidence proves who authorized the change, which version actually committed and what the authoritative system now stores?

WHERE THE MODEL BREAKS

Useful does not mean sufficient.

  1. Missing instrumentation, sampling or exporter loss can create gaps, so a trace should not automatically be treated as complete execution history.
  2. Span status and attributes describe telemetry observations; they do not by themselves prove authorization, idempotent side effects or durable business truth.
  3. Parent-child hierarchy is tree-shaped and cannot represent every async causal relationship; links are required for some producer/consumer flows.
  4. Trace attributes can carry sensitive or high-cardinality data and need explicit governance rather than indiscriminate capture.
