Pydantic AI: make the agent boundary typed before making it bigger

Pydantic AI makes agent I/O, dependencies and tools explicit typed contracts; evals, observability and durable execution remain adjacent quality/runtime capabilities rather than properties of typing itself.

WHY THIS MATTERS

Typed boundaries are a practical way to reduce ambiguity in agent applications without pretending a Python framework alone provides authorization, durable state or production governance.

KNOWLEDGE DELTA

What this source changes in the existing model.

Pydantic AI adds a typed application-boundary model for agent outputs, dependencies, tools and behavioral evaluation. Existing ReAct/controlled-execution/history concepts are suppressed because typing is narrower than those reasoning or production-control responsibilities.

New

Typed agent contract

Source says: The repository emphasizes typed structured outputs and a typed agent API.

Previously: Existing graph concepts describe reasoning, orchestration and governance but not a schema-validated application contract around an agent result.

Project interpretation: Typing turns model output into an explicit runtime boundary for downstream code without claiming semantic correctness.

Source says: Tool signatures/docstrings form schemas and arguments are validated before tool code runs.

Previously: Existing controlled-execution concepts govern consequential work more broadly; they do not represent this code-level schema boundary.

Project interpretation: Tool validation reduces structural interface errors but does not supply authorization or side-effect safety by itself.

MENTAL MODEL

CONTRACT

Typed input / output

Declare the structure the agent is allowed to return and the schemas tools accept.

CONTEXT

Dependencies + tools

QUALITY / RUNTIME

Evals + telemetry + durability

Test, observe or persist the same agent through separate integrations and capabilities.

Source problem

Agent applications often rely on loosely specified model outputs, tool arguments and runtime context, so interface failures appear late and are difficult to reason about.

Source thesis

Use a typed agent object with validated outputs/tools and explicit RunContext dependencies, then compose evaluation, observability and durability around that core contract.

WHERE THE MODEL BREAKS

Useful does not mean sufficient.

  1. Type validation checks structure, not truth, policy compliance or semantic quality.
  2. Validated tool arguments do not make a consequential side effect authorized or idempotent.
  3. Pydantic Evals is an evaluation surface but is not identical to historical replay evaluation in the existing production-agent model.
  4. Durable execution is provided through integrations/capabilities and should not be attributed to the core typed loop by default.
