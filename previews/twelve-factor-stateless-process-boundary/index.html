Twelve-Factor processes: disposable compute, durable state elsewhere

A twelve-factor process is stateless and share-nothing: persistent correctness state belongs in backing services, while local memory or disk is only disposable working cache.

WHY THIS MATTERS

'Stateless' is easy to misunderstand as 'the application has no state.' The useful boundary is narrower: process instances must be disposable because the next request/job may run elsewhere, so anything that must survive belongs outside the process. That same separation remains useful even for modern long-running work, provided durable orchestration state also lives outside disposable compute.

KNOWLEDGE DELTA

What this source changes in the existing model.

Twelve-Factor adds a process-lifetime boundary rather than another workflow runtime: compute processes are disposable, durable correctness state belongs in backing services, and local memory/files are acceptable only when their loss is safe.

Stateless process

New

Backing-service state

Source says: Any data that must persist is stored in a stateful backing service rather than process memory or local filesystem.

Previously: No prior concept explicitly represented the application-level rule that durable correctness state must survive outside disposable compute processes.

Project interpretation: The application can remain stateful while compute stays replaceable because persistence has an explicit external owner.

Prior evidence: No prior project evidence — baseline/new knowledge.
New

Ephemeral process state

Source says: Memory and local filesystem may be used as brief single-transaction cache but must not be required by future requests/jobs.

Previously: The existing graph did not distinguish safe temporary process-local working data from durable application state.

Project interpretation: This avoids the overcorrection that stateless architecture forbids all local state; the real test is whether losing it breaks correctness.

MENTAL MODEL

01 · Handle

Disposable process

A process handles the current request or job without assuming future affinity.

02 · Cache

Temporary local work

Memory or local files may hold short-lived data that can be discarded or recomputed.

03 · Persist

Backing service

Anything needed by future work is written to a durable stateful service.

04 · Replace

Any next process

A different or restarted process can continue future requests because correctness did not depend on the old local state.

Source problem

Scaling, restart, deploy or relocation means a future request/job cannot rely on hidden state inside the process instance that handled earlier work.

Source thesis

Keep processes stateless/share-nothing, store persistent data in stateful backing services, and use process-local memory/files only as short-lived disposable cache whose loss does not break correctness.

Persistent application state remains necessary; it is deliberately externalized from disposable compute.

learn

EXAMPLES

web session

A user request lands on a different process than the previous request.

Does the session survive because it lives in a backing store, or did the application silently depend on sticky routing and process memory?

background job

A worker downloads a large file, transforms it and writes the result.

Can the local file disappear after the work unit because the durable result has already been persisted elsewhere?

long-running workflow

A worker process is restarted while a multi-day business workflow is waiting.

Is durable workflow progress outside the disposable worker, or was process-local memory accidentally treated as orchestration state?

WHERE THE MODEL BREAKS

Useful does not mean sufficient.

  1. Stateless processes do not imply a stateless application; the factor explicitly relies on stateful backing services.
  2. Externalizing state introduces network, consistency and backing-service failure modes that this source does not solve.
  3. The factor does not define durable workflow execution; modern workflow state can remain external while workers themselves stay disposable.
  4. Process-local storage is not forbidden when used as disposable cache or temporary working data whose loss does not violate correctness.

PERSONAL ACTION MAP

Convert understanding into a decision.

Use now
  • For each service or worker, list the data whose loss on restart would break correctness; anything on that list should not exist only in process memory/local disk.
  • Distinguish disposable cache from durable state instead of banning local state categorically.
Try
  • Restart or replace one service instance mid-flow and verify that later requests/jobs can continue without session affinity or hidden local files.
Learn
  • backing-service failure semantics
  • session state
  • durable orchestration state
  • process lifecycle
Build
  • A small two-instance demo where requests alternate between processes while shared session/work state remains in an external store.
Watch
  • Where externalizing high-volume intermediate state adds unnecessary latency and should remain recomputable local cache instead.
Ignore for now
  • Equating generic twelve-factor processes with Temporal-specific Worker, Workflow or Activity concepts.
