Temporal: the mental model behind durable execution

Temporal moves workflow progress out of one process and into durable execution state so Workers can fail, restart and continue the work.

WHY THIS MATTERS

Retries are easy to describe and surprisingly hard to compose across multi-step, long-running work. Temporal is useful to understand because it changes the unit of reliability from a running process to a persisted Workflow Execution.

KNOWLEDGE DELTA

What this source changes in the existing model.

Temporal turns the earlier generic idea of durable, reconstructable execution into a concrete workflow-runtime model.

MENTAL MODEL

01 · Start

Workflow Execution

A client starts durable work whose identity and progress live beyond one Worker process.

02 · Persist

Event History

The Temporal Service records Events in an append-only history representing Workflow Execution state.

03 · Dispatch

Task Queue

Workflow and Activity tasks are made available for Worker Processes to poll and execute.

04 · Execute

Worker + Activity

Workers run application code; side-effecting work can retry and therefore needs safe external-operation semantics.

05 · Recover

Replay and continue

If a Worker disappears, persisted history remains and workflow state can be reconstructed so execution continues.

Source problem

Long-running or multi-step processes become fragile when their progress exists mainly inside one process and every failure path must be rebuilt manually.

Source thesis

Temporal provides durable execution by persisting Workflow Execution state and progress in the Temporal Service while Worker Processes execute tasks from queues.

CONCEPTS TO KNOW

Learn only the prerequisites that preserve the model.

learn

Workflow Execution

This is the durable unit of execution; it is not equivalent to one running Worker process.

learn

Event History

Temporal defines it as an append-only log of Events representing the full state of a Workflow Execution.

learn

Worker Process + Task Queue

Workers poll queues and execute code, which separates durable workflow state from any single executor process.

learn

Activity Execution

Activities are the practical boundary for work that interacts with external systems and can be retried.

learn

Idempotency under retry

A retry can repeat external work; Temporal's documentation explicitly calls for idempotent Activity design to avoid duplicate effects.

EXAMPLES

custom automation

A multi-step onboarding process waits for external APIs, human input and later retries.

Should progress survive process restarts without writing custom recovery tables and retry orchestration for every step?

AI agent

An agent workflow invokes tools over minutes or hours and may wait for approval or external results.

Is the agent loop important enough that a Worker restart should not erase which steps already completed or what should happen next?

WHERE THE MODEL BREAKS

Useful does not mean sufficient.

  1. Temporal introduces a workflow runtime, SDK programming model and service dependency; simple stateless request-response or short best-effort jobs may be better served by lighter infrastructure.
  2. Retries do not make external effects exactly-once. Activities that can be retried still need idempotent or otherwise safe interactions with external systems.
  3. Workflow logic must respect Temporal's replay/execution model; arbitrary non-deterministic behavior cannot be treated like ordinary in-process code.
  4. This explainer deliberately stops before advanced history lifecycle, deployment versioning, replication, scaling and Cloud operations.
