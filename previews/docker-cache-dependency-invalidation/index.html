Docker build cache: invalidation is a dependency-graph problem

Fast Docker builds come from drawing better dependency boundaries: keep stable expensive inputs early, volatile inputs late, and reusable/transient data out of ordinary layer invalidation when possible.

WHY THIS MATTERS

Build caching is often treated as a list of tricks. The stronger mental model is dependency propagation: each layer depends on an instruction and inputs, and an early invalidation can fan out into expensive downstream rebuilds. Once seen this way, layer order, context size and mounts become different ways to control the same dependency boundary.

What this source changes in the existing model.

Docker build caching adds a new build-systems domain to the graph. Prior retrieval correctly found no close concepts, so the case introduces cache dependency boundaries and invalidation cascades without merging them into workflow checkpoints, database checkpoints or agent memory.

New

Build-cache dependency boundary

Source says: Docker reuses a layer only while its instruction and dependent files remain unchanged, making cache reuse depend on explicit inputs.

Previously: The graph has persistence and checkpoint concepts in other domains, but no concept for build-result reuse controlled by instruction/input stability.

Project interpretation: Layer ordering and build-context design are best understood as editing the dependency boundary around expensive work.

New

Cache invalidation cascade

Source says: Docker documentation states that a changed step causes following steps to rebuild, so frequent changes early in a Dockerfile amplify downstream work.

Previously: No current concept captures downstream build-cost fan-out caused by an upstream cache miss.

Project interpretation: The optimization target is not maximal caching in general; it is minimizing unnecessary invalidation fan-out from volatile inputs.

Persistent build cache

Source says: Cache mounts retain package caches across layer rebuilds, and external caches allow cache reuse across different builders/environments.

Previously: Existing durable-state concepts have different semantics and should not be reused merely because data persists across runs.

Project interpretation: Persistent build cache is a cost-reduction mechanism for recomputation/downloads, not authoritative workflow or business state.

MENTAL MODEL

01 · Change

An instruction or file dependency changes, so that cached layer can no longer be reused.

→
02 · Cascade

Every downstream layer must execute again even when much of its logical work is unchanged.

→
03 · Design

Reorder stable work, shrink context and move reusable/transient data into appropriate mounts or external caches.

Source problem

Small or irrelevant input changes can invalidate a cached layer and amplify rebuild cost through later expensive Dockerfile steps.

Source thesis

Design cache boundaries around dependency stability: isolate stable expensive work, minimize volatile inputs, and use build mounts/external caches when reusable data should outlive ordinary layer rebuilds.

EXAMPLES

Node.js image

COPY . . occurs before npm install, so editing one source file invalidates dependency installation.

Can package manifests be copied and dependencies installed before volatile application source is copied?

large build context

Temporary files, logs or node_modules are sent to the builder although they are not real inputs.

Can .dockerignore or a bind mount remove these files from persistent cache dependencies?

CI

Every build runs on a fresh builder with no local cache.

Would a remote cache reduce repeated compilation/download cost enough to justify the extra cache lifecycle?

WHERE THE MODEL BREAKS

Useful does not mean sufficient.

  1. A cache optimization is valid only if the cache boundary still includes every input that semantically affects the result.
  2. Layer reordering can create stale or confusing results if hidden dependencies are omitted merely to preserve cache hits.
  3. External caches add access-control, storage and retention concerns and may be unnecessary for small local builds.
  4. Package-manager cache mounts have tool-specific sharing and locking requirements.
