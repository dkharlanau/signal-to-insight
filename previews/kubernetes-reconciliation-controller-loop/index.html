Kubernetes controllers: reconcile desired state, do not script the happy path

A Kubernetes controller is a continuing reconciliation loop: observe current state, compare it with declared desired state, make or request a change, then observe again.

WHY THIS MATTERS

The controller model is a compact way to understand resilient automation under constant change. It replaces one-shot procedural assumptions with repeated convergence toward a declared target, while keeping each controller focused on a bounded responsibility.

KNOWLEDGE DELTA

What this source changes in the existing model.

Kubernetes adds a distinct state-convergence model rather than another durable-workflow mechanism: the source introduces reconciliation, desired state and observed state while the retrieved Temporal/control concepts are deliberately suppressed as different responsibilities.

New

Reconciliation loop

Source says: The Kubernetes controller pattern repeatedly observes current state and makes or requests changes that move the system toward desired state.

Previously: The existing graph models durable workflow progress, execution control and agent loops, but it does not model persistent convergence of a declared state invariant.

Project interpretation: Reconciliation becomes a separate reusable automation model: success is not one completed run but continued correction whenever reality drifts from the target.

Desired state

Source says: A Kubernetes resource specification declares what state should be true independently of what is currently true.

Previously: No prior concept explicitly represented a declarative target state as the reference point for continuous corrective automation.

Project interpretation: Separating target state from execution history makes it possible to reason about drift after any individual workflow or command has finished.

New

Observed state

Source says: Controllers use feedback about current reality to determine whether corrective action is required before observing again.

Previously: Earlier graph concepts record execution state or observations inside other mechanisms, but not the current-state side of a desired-versus-observed convergence loop.

Project interpretation: Observed state becomes the feedback half of reconciliation and prevents declarative intent from being mistaken for proof that the system is actually correct.

MENTAL MODEL

01 · Declare

Desired state

A resource spec states what should be true.

02 · Observe

Current state

The controller inspects what is actually true now.

03 · Compare

Find the delta

The controller determines whether reality is close enough to the desired state.

04 · Act

Make a bounded change

The controller changes an API object or an external system to reduce the delta.

05 · Repeat

Observe again

The loop continues because the system can change again after any successful action.

Source problem

A distributed system is continuously changing: resources fail, external systems drift, and one successful command does not guarantee that the intended state remains true.

Source thesis

Represent desired state declaratively and use independent control loops that repeatedly observe current state and act to move it closer to the desired state.

Core topics
  • desired state versus current state
  • non-terminating reconciliation loop
  • control through the Kubernetes API
  • direct control of external systems
  • small focused controllers instead of one monolithic control loop
  • continuous convergence rather than stable completion

EXAMPLES

Kubernetes Job

A Job object declares that work should complete, while Pods are the resources that actually run the work.

Can the Job controller keep creating or observing the required Pods until current state reflects the Job's desired outcome?

external infrastructure

A controller manages something outside the cluster such as node capacity.

Can it observe desired state from the API, change the external system, and then report/observe the resulting state without assuming the first external call is final?

business automation

A record should exist in several systems, but one downstream copy can disappear or lag after an earlier successful run.

Would expressing the target state and periodically reconciling observed state be safer than treating the original workflow run as permanent proof of correctness?

WHERE THE MODEL BREAKS

Useful does not mean sufficient.

  1. Reconciliation does not remove the need for safe repeated side effects; a controller can still cause duplicates or oscillation if its actions are not designed for repetition.
  2. Desired state can be wrong. A controller faithfully converging on a bad specification is still a failure.
  3. Multiple controllers can interact through shared resources, so bounded responsibility reduces coupling but does not eliminate coordination problems.
  4. The controller pattern is not the same as durable workflow execution: it focuses on continuously converging state, whereas a workflow engine may preserve the progress of a particular long-running execution.

PERSONAL ACTION MAP

Convert understanding into a decision.

Use now
  • When designing automation, distinguish a target condition that must remain true from a one-time sequence that merely attempted to create it.
  • For long-lived invariants, ask what observes drift after the original workflow finishes.
Try
  • Model one operational invariant as desired state + observed state + reconciliation action instead of a procedural retry script.
Learn
  • controller reconciliation
  • desired-state systems
  • safe repeated side effects
  • control-loop decomposition
Build
  • A tiny reconciler that compares a declarative JSON target with observed state and emits only the corrective action required to close the delta.
Watch
  • How controller-runtime implementations handle retries, backoff, event coalescing and stale observations.
Ignore for now
  • Treating every business workflow as a Kubernetes-style controller; use reconciliation only where a persistent target state exists.
