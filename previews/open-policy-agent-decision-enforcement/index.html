Open Policy Agent: separate policy decisions from enforcement

OPA makes policy a separate decision step: the application supplies context, OPA evaluates Rego and data, returns a decision, and the application remains responsible for enforcement.

WHY THIS MATTERS

Policy-as-code becomes much more concrete once the trust boundary is clear. OPA does not perform the protected action and it does not magically enforce its answer; it gives an application a separately versioned, testable decision engine while the application stays the enforcement point.

MENTAL MODEL

03 · Management

Policy source + bundles + status/logs

Version and distribute policy/data separately, then observe which policy and runtime state produced decisions.

02 · Decision

OPA / PDP · input + Rego + data → decision

OPA receives structured context, evaluates declarative policy and returns an allow/deny or richer result.

01 · Enforcement

Application / PEP

The application owns the real operation and must actually accept, reject or alter behavior based on OPA's decision.

Source problem

Policy rules become difficult to review, change and keep consistent when authorization and operational decisions are hardcoded across many services.

Source thesis

OPA decouples policy decision-making from enforcement by evaluating declarative Rego policy plus data against structured input and returning a decision to the integrating application.

CONCEPTS TO KNOW

Learn only the prerequisites that preserve the model.

learn

Policy Decision Point (PDP)

OPA computes the policy result; understanding this boundary prevents treating the policy engine as the component that performs the protected action.

learn

Policy Enforcement Point (PEP)

The integrating application remains responsible for obeying the decision, so enforcement code is still part of the trusted boundary.

learn

Rego + structured input

OPA evaluates declarative rules over structured request/context data and loaded policy data rather than owning the surrounding application workflow.

know

Policy bundles

Bundles show how policy/data can move on a lifecycle separate from application deployment while distributed OPA instances remain close to enforcement.

know

Decision logs

Policy decisions can become operational evidence, but the logged input/output may require deliberate masking of sensitive fields.

EXAMPLES

API authorization

A service receives a request and needs to decide whether a user may call an operation on a resource.

Can the service delegate the policy decision to OPA while still retaining responsibility for accepting or rejecting the request?

AI agent tool execution

An agent wants to perform a consequential operation such as modifying a customer record or invoking an administrative API.

Can the execution service ask OPA whether this actor, tool and resource combination is permitted before it performs the operation?

platform policy

A deployment platform needs rules about where workloads may run or which metadata must exist before provisioning.

Can policy change without scattering another set of hardcoded conditionals across each platform component?

WHERE THE MODEL BREAKS

Useful does not mean sufficient.

  1. OPA returns decisions but does not force an application to obey them; the PEP remains part of the trusted computing boundary.
  2. Policy-as-code does not require one remote central policy service. OPA can be distributed close to enforcement while management is logically centralized.
  3. Bundle distribution is not equivalent to instantaneous global consistency, so policy versions and rollout state matter during change.
  4. Decision inputs and logs can contain sensitive context; masking and data-minimization rules must be deliberate.
  5. A policy engine makes rules executable and testable but does not determine whether the organization's policy itself is correct.

PERSONAL ACTION MAP

Convert understanding into a decision.

Use now
  • When reviewing authorization architecture, separate the question 'who computes the policy decision?' from 'who actually enforces the result?'
Try
  • Use the Rego Playground or OPA CLI to write one allow/deny rule over a small JSON input such as actor, operation and resource.
  • Change the policy while keeping the same input/request shape, then observe that the decision changes without changing the calling application logic.
  • Run OPA as a local service and make one REST decision request so the PDP/PEP boundary becomes concrete.
Learn
  • Rego documents, rules and structured input
  • Policy Decision Point versus Policy Enforcement Point
  • OPA bundle distribution and policy versioning
  • Decision Logs, status reporting and sensitive-data masking
Build
  • A tiny policy gate in front of one agent/tool action that records the decision ID and policy version alongside the execution result.
Watch
  • How agent platforms standardize policy-decision interfaces and connect them to signed policy bundles, identity and execution ledgers.
Ignore for now
  • Deep Kubernetes admission, Terraform, SSH and ecosystem-specific OPA integrations until the basic decision/enforcement model is clear.
