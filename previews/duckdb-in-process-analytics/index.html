DuckDB: move the analytical engine into the application process

DuckDB makes analytical SQL a composable in-process capability, so a tool can query host data and files without first turning the database into a separately operated service; Quack is now extending that foundation with an explicit remote mode.

WHY THIS MATTERS

The important architectural shift is not simply another SQL dialect. In-process execution changes the deployment boundary: analytics can become a library capability inside the consuming program, host data can stay close to the query engine, and Parquet/CSV can remain directly queryable. That simplicity still has a write-ownership boundary, and DuckDB's emerging Quack mode should be treated as an additional architecture rather than evidence that the in-process model never mattered.

Source problem

Analytical tools often add service setup, network boundaries and explicit data-loading steps before SQL can be used on data that already lives inside an application or in analytical files.

Source thesis

DuckDB embeds an analytical SQL engine in the host process so applications can query host objects and files through native clients without requiring a separate database server for the core workflow; the same model centers stable read-write ownership in one process, while Quack adds an explicit remote/client-server path.

WHERE THE MODEL BREAKS

Useful does not mean sufficient.

  1. In-process deployment couples engine lifecycle and resource use more closely to the host process and is not a universal replacement for a shared database service.
  2. The core stable read-write model centers ownership in one process; MVCC/OCC make writer threads concurrent inside that boundary rather than automatically coordinating arbitrary writer processes.
  3. Direct file querying can reduce ingestion and storage duplication but performance depends on file layout, storage latency, query reuse and workload shape.
  4. MVCC reinforces a known database-concurrency primitive but does not make DuckDB's process topology equivalent to PostgreSQL's deployment model.
  5. Quack/client-server support is actively evolving toward v2.0 and should be re-analyzed after stabilization.
