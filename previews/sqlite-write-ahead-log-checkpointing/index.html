SQLite WAL: commit by append, consolidate by checkpoint

SQLite WAL keeps the database file stable during commit, appends changed pages to a log, gives readers fixed end marks, and moves committed changes back later through checkpointing.

WHY THIS MATTERS

WAL is a useful mental model for separating foreground commit from later consolidation. The separation improves reader/writer concurrency but introduces a third operation—checkpointing—with its own blocking, durability and file-growth trade-offs.

MENTAL MODEL

01 · Write

Append changed pages

The writer appends new page versions to the WAL instead of overwriting the database file.

02 · Commit

Append commit record

The transaction becomes committed when the WAL receives its commit marker.

03 · Read

Freeze an end mark

Each reader uses a fixed end mark and sees page versions no newer than that snapshot boundary.

04 · Consolidate

Checkpoint

Committed WAL pages are copied back to the database when active readers permit it.

05 · Reuse

Recycle WAL space

After checkpoint progress and reader release allow it, SQLite can rewind/reuse the WAL instead of growing forever.

Source problem

Rollback journaling writes old pages aside and then changes the database file, coupling commit behavior to the main database and limiting concurrency.

Source thesis

Append changed pages and a commit record to a WAL, let each reader read through a stable end mark, and checkpoint committed WAL pages back into the database later.

EXAMPLES

embedded application

A UI reads data while a background task commits small updates.

Can readers keep stable snapshots while the writer appends commits, and what checkpoint policy prevents the WAL from becoming the new latency problem?

long-running report

A read transaction stays open while writes continue.

Will the reader's end mark prevent checkpoint completion and cause WAL growth or slower later reads?

WHERE THE MODEL BREAKS

Useful does not mean sufficient.

  1. WAL requires shared-memory coordination and therefore normally keeps all database processes on the same host rather than a network filesystem.
  2. Readers do not block the writer, but SQLite still has one writer at a time.
  3. Long-running readers can starve checkpoint completion and let the WAL grow.
  4. Checkpoint and synchronous settings trade foreground latency against durability after power loss; WAL is not a free universal speed-up.
